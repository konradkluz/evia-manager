# `@evia/api` — API EVia Manager (NestJS)

Szkielet z EVM-008 (AC1, AC2, AC4; ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0013). Modularny monolit NestJS 12 (Express 5), PostgreSQL przez Kysely, kontrakt z `@evia/contracts`.

## Polecenia
| Polecenie | Co robi |
|---|---|
| `pnpm --filter @evia/api run build` | `tsc` → `dist/` (NestJS wymaga dekoratorów, których Node nie usuwa) |
| `pnpm --filter @evia/api run start` | `node dist/src/main.js` — wymaga zmiennych z `.env.example` |

| `pnpm --filter @evia/api run db:migrate` | migracje „w przód” (Kysely `Migrator`); nigdy przy starcie API; czyta tylko `DATABASE_URL`, `NODE_ENV` i `LOG_LEVEL` (`loadMigrationConfig`) — **bez `CURSOR_KEY`** (EVM-080) |
| `pnpm --filter @evia/api run test:coverage` | testy jednostkowe i HTTP bez bazy, próg 85% linii i gałęzi (warstwa backend) dla kodu niezależnego od bazy; w kontenerze `backend-tests` w ramach `gate:backend` |

## Autoryzacja (deny-by-default)
Każdy handler ma `@OperationId('<operationId z kontraktu>')`; polityka pochodzi wyłącznie z manifestu `@evia/contracts/authz`:
Kolejność kontroli jest stała (szczegóły: `docs/architecture/api-guidelines.md` → Autoryzacja): manifest → operacja publiczna (Origin + Sec-Fetch-Site + limit) → sesja → CSRF → limit logowania i MFA → stan `mfa_enrollment` → kanał → rola → step-up (`403 step_up_required`, tylko operacje z `stepUp: true`) → polityka obiektowa w przypadku użycia (`404`).
1. brak `operationId` lub polityki w manifeście → `403 forbidden` (a przy starcie — błąd: aplikacja nie wstaje, gdy trasa nie ma polityki albo „pożycza” operację o innej metodzie lub ścieżce);
2. `x-evia-authz: { public: true }` → przepuszczone tylko dla operacji z `PUBLIC_OPERATIONS` (dziś `getHealth`, `checkActivationLink`, `setActivationPassword`, `login`, `getLoginPasskeyOptions`, `verifyLoginPasskey`);
3. brak sesji → `401 unauthenticated` (sesja unieważniona → `401 session_revoked`, sesja, której minął czas → `401 session_expired`); nieistniejąca trasa bez sesji też `401` (bez ujawniania mapy tras);
4. mutacja sesji bez poprawnego `Origin`, `Sec-Fetch-Site` i `X-CSRF-Token` → `403 csrf_failed`; sesja `mfa_enrollment` poza operacjami z `MFA_ENROLLMENT_OPERATIONS` → `403 mfa_enrollment_required`; rola lub kanał spoza polityki → `403 forbidden`.
Testy macierzy ról są generowane z kontraktu (`test/authorization/role-matrix.ts`): każda operacja × Administrator / Edytor / Tylko odczyt × `web` / `mobile` × stan sesji + niezalogowany + unieważniona i wygasła sesja, przypadek IDOR dla operacji z parametrem ścieżki, test kompletności i test testu z „dziurawą” polityką.

## Logowanie i sesje (moduł `identity`, EVM-067)
Dwa kroki, wszystkie operacje publiczne, kanał `web` nadaje ścieżka (nie klient). Wartości i mechanizmy (ASVS V6.1.1, V7.1.1):

| Co | Wartość | Gdzie |
|---|---|---|
| bezczynność sesji | **60 min** od ostatniej aktywności | `SESSION_IDLE_MS` (`domain/constants.ts`) |
| limit bezwzględny sesji | **12 h** od zalogowania, nie przesuwa się | `SESSION_ABSOLUTE_MS` |
| zapis aktywności | co najwyżej co 30 s; odczyt sesji (`getCurrentSession`) i `extendSession` nie są aktywnością | `SESSION_TOUCH_INTERVAL_MS`, `PASSIVE_OPERATIONS` |
| `loginToken` (pierwszy krok) | 256 bitów, w bazie tylko SHA-256, **5 min**, jednorazowy, maks. 5 nieudanych prób drugiego kroku (klucz, kod z aplikacji, kod odzyskiwania — wspólny licznik) | `LOGIN_ATTEMPT_TTL_MS`, `LOGIN_MAX_FAILED_SECOND_STEPS` |
| wyzwanie WebAuthn | ≥ 128 bitów (256), w bazie SHA-256, **5 min**, jednorazowe; zużywane przy każdej weryfikacji, nowe opcje unieważniają poprzednie | `CHALLENGE_TTL_MS` |
| wiersze prób logowania | usuwane przy następnym pierwszym kroku, najpóźniej 24 h po wygaśnięciu; brak adresu IP i user agenta w tabeli (RODO — dane klienta tylko w sesji i prefiks w audycie) | `LOGIN_ATTEMPT_RETENTION_MS`, migracja `0006` |
| limit prób | 20 na minutę z jednego IP dla `login`, `getLoginPasskeyOptions`, `verifyLoginPasskey`, `loginTotp`, `loginRecoveryCode`, `startTotpEnrolment`, `confirmTotp` (wspólny), liczony w guardzie przed dostępem do bazy; IP tylko z `request.ip` (`TRUSTED_PROXIES`), nigdy z surowego `X-Forwarded-For`; `429 rate_limited` z `Retry-After` | `AUTHENTICATION_OPERATIONS`, `platform/http/rate-limiter.ts` |

- **Jednakowe odpowiedzi (SR-AUTH-05):** zły e-mail, złe hasło, konto zaproszone i dezaktywowane → ten sam `401 invalid_credentials` (kod, treść, nagłówki) i dokładnie jedna weryfikacja Argon2id — dla konta aktywnego względem jego hasha, w pozostałych przypadkach względem hasha-wabika wygenerowanego przy starcie bieżącymi `ARGON2_PARAMETERS` i weryfikowanego tą samą ścieżką `verify`. Hasło jest normalizowane do NFC (jak przy aktywacji), bez przycinania i zmiany wielkości liter; polityka długości nie obowiązuje przy logowaniu, schemat sprawdza kształt (e-mail ≤ 254, hasło ≤ 1024). Powód porażki trafia tylko do audytu (`login.failed`: `bad_password`, `unknown_user`, `not_active`, `passkey_failed`, `login_expired`; bez hasła, e-maila i jego skrótu) i do metryki `evia_login_failures_total{reason}` (`platform/metrics`; wystawienie do Prometheusa — EVM-007).
- **Drugi krok (SR-AUTH-09):** klucz szukany po `credential_id` **i** koncie z `loginToken` (klucz innego konta = `401 passkey_failed`), `userHandle` musi być kontem, `allowCredentials` tylko z jego kluczami, `userVerification: required`, origin i RP ID z konfiguracji. Sukces w jednej transakcji: atomowe zużycie wyzwania i `loginToken`, ponowna kontrola `users.status` pod blokadą `FOR SHARE`, licznik i `last_used_at` klucza, `lastLoginAt`, nowa sesja (token z CSPRNG), unieważnienie sesji z ciasteczka żądania (`rotated`; przy podwójnym ciasteczku nic) i audyt `login.succeeded`. Dwa równoległe żądania z tą samą asercją dają jedną sesję.
- **Step-up i dziennik audytu (EVM-029; SR-SESS-08, SR-SESS-02):** operacja z `stepUp: true` wymaga uwierzytelnienia kluczem w sesji w ciągu 15 minut (`passkey_authenticated_at`, zegar wstrzykiwany; po roli i kanale, więc E i R dostają `forbidden`); `getStepUpPasskeyOptions` i `stepUp` (limit 20/min/IP): wyzwanie o celu `passkey_step_up` powiązane z sesją, asercja tym samym kodem co logowanie (`passkey-assertion.ts`), sukces w jednej transakcji — warunkowy `UPDATE` kończy sesję (`rotated`), nowa sesja z nowym tokenem i CSRF, limit 12 h bez zmian; porażka → `401 passkey_failed` i `step_up.failed`, sesja bez zmian. `listAuditEvents`: kursor nieprzezroczysty (EVM-080; ten sam kodek co pozostałe listy, operacja `listAuditEvents`, użytkownik, skrót filtrów `action` / `actorUserId` / `outcome` / `from` / `to` tak, jak je podano w żądaniu — bez `limit`; pozycja `[asOf, occurred_at, id]` jest zaszyfrowana, a `asOf` to koniec okresu pierwszej strony, więc domyślny okres „30 dni do teraz” nie przesuwa się między stronami; zły, cudzy, wygasły lub z innej operacji kursor to jedno `400 invalid_cursor`, kursor o złym kształcie — `validation_failed`; strażnik rozstrzyga o roli i step-upie przed otwarciem kursora), jawna lista kolumn, `audit.read` w tej samej transakcji (fail closed), nazwy osób przez fasadę `UserDirectory.displayNamesOf`.
- **Wygasanie (SR-SESS-03):** wszystkie stany sesji (`active`, `mfa_enrollment` z linkiem i bez); kolejność: unieważniona → wygasła → dopiero potem przesunięcie bezczynności warunkowym `UPDATE` (wygasła sesja nie wraca). Wygasła sesja: `401 session_expired`, `session.expired` w audycie dokładnie raz (`revoke_reason = 'expired'`). Czas rzeczywisty z wstrzykiwanego zegara.
- **Sesja `mfa_enrollment` po samym haśle** (konto aktywne bez drugiego kroku): bez linku, nie może zarejestrować czynnika (`registerPasskey`, `startTotpEnrolment` i `confirmTotp` odrzucone `403`); dodanie czynnika po samym haśle — nigdy (SR-AUTH-13, AB-01).

## Kod z aplikacji (TOTP) i kody odzyskiwania (moduł `identity`, EVM-023)
Drugi krok bez sprzętu: kod z aplikacji uwierzytelniającej i 10 kodów odzyskiwania. Specyfikacja: `packages/contracts/openapi/paths/identity.yaml` (`loginTotp`, `loginRecoveryCode`, `startTotpEnrolment`, `confirmTotp`, `generateRecoveryCodes`, `stepUp` z `method: totp`).

| Co | Wartość | Gdzie |
|---|---|---|
| kod z aplikacji | 6 cyfr, okres 30 s, tolerancja ±1 krok, **każdy krok tylko raz** (jeden `last_used_step` dla logowania, step-upu i potwierdzenia konfiguracji; zużycie warunkowym `UPDATE … WHERE last_used_step IS NULL OR last_used_step < :krok`) | `otpauth` 9.5.2 za portem `TotpEngine` (`infrastructure/totp-engine.ts`), `domain/totp.ts` |
| sekret | 160 bitów z CSPRNG, w bazie **tylko szyfrowanie kopertowe** (losowy DEK 256 bit na wartość, owinięty AES-256-GCM kluczem głównym; nagłówek: wersja, algorytm, id klucza + kontekst `totp:<userId>` jako AAD obu operacji); nieaktywny (`pending`) do potwierdzenia poprawnym kodem — wtedy nie jest metodą drugiego kroku | `platform/crypto/field-encryption.ts`, `application/totp-secret.ts`, tabela `identity.totp_factors` |
| klucze główne | `FIELD_ENCRYPTION_KEYS` (`id:base64url32,…`, pierwszy szyfruje, wszystkie odszyfrowują); **produkcja bez klucza, z zaślepką, z kluczem ≠ 32 B, z powtórzonym id albo równym `CURSOR_KEY` nie startuje**; poza produkcją pusty = konfiguracja kodu z aplikacji niedostępna (`503`), nic nie trafia do bazy jawnie; `db:migrate` nie czyta | `platform/config/config.ts`, `.env.example` |
| konfiguracja (enrolment, confirm) | **tylko sesja `mfa_enrollment` związana z linkiem jednorazowym** (jak rejestracja klucza dostępu; sesja z samego hasła → `403`); Administrator w panelu → `403` (manifest nie ma tej roli; usługa czyta rolę z bazy); konto z aktywnym drugim krokiem → `409 mfa_already_configured`; potwierdzenie w jednej transakcji (link, aktywacja konta, nowa sesja `active` z oknem step-upu, e-mail, audyt) | `application/totp-enrolment.service.ts` |
| metody drugiego kroku | `secondStepMethods(userId, kanał)` — jedna funkcja dla logowania, resetu hasła i komponera e-maila: klucz dostępu, aktywny TOTP (nigdy Administrator w panelu), kody odzyskiwania tylko obok czynnika; rola z bazy w chwili żądania | `application/second-step.ts` |
| logowanie kodem | `loginToken` → konto (rola z bazy) → kod → krok → zużycie `loginToken` → sesja; porażki (zły kod, powtórzony kod, Administrator w panelu) liczone na `loginToken` **razem z kluczem dostępu i kodem odzyskiwania** (piąta kończy próbę) i audytowane `login.failed` z kontem — liczy je też blokada konta (EVM-026); konto blokowane `FOR UPDATE` jako pierwszy zamek (bez zakleszczeń) | `application/login-totp.service.ts`, `login-attempt.ts` |
| step-up kodem | Edytor i Tylko odczyt (Administrator → `403`); licznik porażek **na sesji**: piąty zły kod unieważnia sesję (`401 session_revoked`, `revoke_reason step_up_failed`); nowa sesja z `totp_authenticated_at`, limit 12 h bez zmian; `stepUpFresh` = późniejsze z (klucz, kod); kod odzyskiwania nie działa w step-upie | `application/step-up.service.ts`, `domain/session-policy.ts` |
| kody odzyskiwania | 10 × 20 znaków base32 (100 bitów, CSPRNG), w bazie tylko Argon2id, pokazane raz (`Cache-Control: no-store`, brak operacji odczytu); generowanie: **konto bez kodów albo odświeżenie przez sesję, która wygenerowała bieżące** (`recovery_codes.session_id`), inaczej `403 recovery_codes_regeneration_unavailable` (zmiana z konta — EVM-028); wymaga świeżego step-upu | `application/recovery-code.service.ts` |
| logowanie kodem odzyskiwania | kolejność: `loginToken` → kształt kodu (po pominięciu wielkości liter, spacji i myślników) → Argon2id (≤ 10 weryfikacji, bez transakcji) → jedna transakcja: zużycie kodu i `loginToken`, e-mail, `remainingCodes` po zużyciu; sesja bez okna step-upu | `application/login-recovery-code.service.ts` |
| limit | wszystkie operacje drugiego kroku i konfiguracji w **jednym** kubełku `authentication` (20/min/IP, wspólnym z hasłem i kluczem dostępu) | `AUTHENTICATION_OPERATIONS` |
| e-maile i audyt | `mfa_changed` (`totp_enrolled`, `recovery_codes_generated`) i `recovery_code_used` przez skrzynkę nadawczą (`MfaEmailComposer`); zdarzenia `mfa.totp_enrolled`, `mfa.recovery_codes_generated`, `login.recovery_code_used`, `login.failed` (`totp_failed`, `recovery_code_failed`), `step_up.*` — bez sekretu, adresu `otpauth`, kodów i ich pozycji | `application/mfa-email.composer.ts`, `events.ts` |
| logi | klucze `secret`, `otp*`, `codes`, `recoverycode*` są redagowane (samo `code` nie — to kod błędu RFC 9457) | `platform/logging/logger.ts` |

- **Operacja nazywa się `startTotpEnrolment`** (ścieżka `/api/v1/account/totp/enrolment`), nie `setupTotp`: test EVM-016 zabrania w kontrakcie ścieżek ze słowem „setup” (brak endpointu instalacyjnego pierwszego administratora).
- **Brak klucza szyfrowania lokalnie:** `compose.dev.yaml` i `dev:init` nie przekazują jeszcze `FIELD_ENCRYPTION_KEYS` do kontenera API (zadanie infrastruktury) — do tego czasu konfiguracja kodu z aplikacji odpowiada `503`.
- **Utrata `FIELD_ENCRYPTION_KEYS` = utrata dostępu wszystkich użytkowników z TOTP** (sekretów nie da się odszyfrować; ich odzyskanie to reset drugiego kroku). Klucz trafia do inwentarza kluczy (SR-CRYPTO-04), kopii w Bitwarden i zestawu offline (EVM-007).

## Katalog i szablony (moduł `catalog`, EVM-019)
- **Dane startowe** to migracja danych `0008_catalog_seed` (schemat `0007_catalog`) z zamrożonej kopii `src/migrations/data/catalog-seed-2026-10.ts` wg `docs/product/service-catalog.md`: 12 pozycji katalogu, 10 szablonów procesów (32 etapy), 16 rodzajów dokumentów, 5 szablonów zleceń (26 pozycji, 11 transz). Zmiana danych = **nowa migracja danych z własną zamrożoną kopią** (nigdy edycja starej); migracje nie czytają zegara bazy (stały znacznik czasu w danych) i wstawiają wartości tylko jako parametry.
- **Tylko do odczytu:** rola `evia_app` ma `USAGE` na schemacie i jawne `SELECT` na każdej tabeli, nic więcej (bez `ALTER DEFAULT PRIVILEGES`); kontrakt nie ma operacji `POST`/`PUT`/`PATCH`/`DELETE` w `/api/v1/catalog` (edytor — M4). Testowe wycofanie szablonu (`is_active = false`) robi rola migracyjna.
- **Operacje** (wszystkie `GET`, role Administrator / Edytor / Tylko odczyt, kanał `web`, bez audytu — odczyt konfiguracji nie jest zdarzeniem wrażliwym): `listWorkOrderTemplates` (`?siteTypeHint=`, tylko aktywne), `getWorkOrderTemplate` (po `templateId`, także wycofany; nieznany → `404 not_found`, zły format → `400 validation_failed`), `listServiceItems`, `listProcedureTemplates`, `listDocumentKinds`. Zbiory są małe i zwracane w całości w kopercie `{ items, nextCursor: null }` (≤ 100 elementów — pilnuje test spójności); `limit` i `cursor` nie są deklarowane (→ `400 unknown_parameter`) do czasu edytora w M4. Odpowiedź jest walidowana schematem kontraktu, a nagłówek to wyłącznie globalne `Cache-Control: no-store`. Procesy podglądu szablonu to procesy wnoszone przez jego pozycje (współdzielony proces — raz).
- **Zestawy parametrów** (`domain/parameter-sets.ts`): `charger_spec`, `charger_installation`, `supply_circuit`, `connection_power`, `dso_request` — ścisłe (bez pól dodatkowych, także `__proto__`), zakresy liczb, tekst NFC bez znaków sterujących, ≤ 16 KB JSON-a w bajtach UTF-8 (to samo `octet_length` w CHECK kolumny `default_parameters`). - **Kolejność w transakcji** (`application/transition-work-order.service.ts`, komentarz na górze pliku): blokada wiersza `SELECT … FOR UPDATE` z polityką odczytu (`404`) → `If-Match` (`428` / `400`) → treść (`400`) → idempotencja (przed porównaniem wersji; zakres rekordu zawiera id zlecenia) → krawędź tabeli (`409`, a przy nieaktualnej wersji `412`) → rola (`403`) → step-up przy przywróceniu (`403 step_up_required`, `stepUpFresh` z `identity` i `CLOCK`) → wersja (`412`) → pola przejścia → warunki uczestników (`422`) → `UPDATE … version = version + 1`, skutki uczestników, zdarzenie audytu. Błąd na dowolnym kroku cofa całość.
- **Port `WorkOrderTransitionParticipant`** (`transition-participant.ts`, rejestr `WorkOrderTransitionRegistry` eksportowany z modułu): `check` (kod powodu albo `undefined`) i `apply` w transakcji komendy, stała kolejność, bez zewnętrznego I/O. Brak uczestników produkcyjnych do EVM-053 (warunki spełnione); testy mają uczestnika testowego.
- **`If-Match`** (`platform/http/if-match.ts`): silny ETag `"N"` (zdolność platformy — pierwsze użycie); nowe kody `invalid_state_transition` (409), `version_conflict` (412), `transition_condition_not_met` (422), `precondition_required` (428).
- **Powód** (`status_reason`) to pole swobodne z danymi osobowymi: zostaje w kolumnie (do wpisu dziennika, EVM-038), a odczyt go nie zwraca; nigdy w audycie, logu, odpowiedzi ani rekordzie idempotencji.
- **Migracja `0016_work_order_status`** (expand): kolumny `resume_status` (cztery statusy aktywne), `status_reason` (1–500), `status_changed_at`, `closed_at`, `completed_on` — wszystkie nullable, bez backfillu.
- **Dług / uwagi:** `PATCH` pola `status` (`400 read_only_field`) — test w EVM-035 (`work-order-editing.test.ts`); brak limitu mutacji na użytkownika (SR-API-02 → EVM-067); audyt odmów przywrócenia (`outcome: denied`) — przegląd modelu zagrożeń w M1.

## Procesy i etapy zlecenia (moduł `procedures`, EVM-031)
- **Operacje:** `listWorkOrderProcedures` (`GET /api/v1/work-orders/{workOrderId}/procedures`; A / E / R, kanał `web`) i `updateProcedureStage` (`PATCH /api/v1/work-orders/{workOrderId}/procedure-stages/{stageId}`; A / E, kanał `web`, audyt `procedure_stage.updated`; `If-Match` wymagany, `Idempotency-Key` opcjonalny). Zmienia się tylko osoba odpowiedzialna i termin; status etapu to komenda EVM-032. Zleceniu odpowiada fasada `WorkOrderDirectory` modułu `work-orders` (`findVisible`, `lockVisible` — polityka odczytu w zapytaniu, `closed` = Rozliczone albo Anulowane).
- **Status etapu** (EVM-032): `transitionProcedureStage` (`POST …/procedure-stages/{stageId}/transitions`; A / E, kanał `web`, audyt `procedure_stage.transitioned` bez powodu blokady, strony i dat) wykonuje wiersze tabeli przejść etapu (`domain/stage-transitions.ts`, 16 wierszy) w jednej transakcji z blokadą zlecenia, etapu i strony (fasada `PartyDirectory`); reguła „na kogo czekamy” (`domain/waiting.ts`) jest wspólna z `PATCH` („Zmień, na kogo czekamy…”). Wspólne: `application/stage-answer.ts`. Szczegóły: `docs/architecture/api-guidelines.md`.
- **Kompozycja** (`application/procedures-contributor.ts`): kontrybutor rejestruje się w `WorkOrderCompositionRegistry` (`order` 100 — przed płatnościami), czyta procesy szablonu przez `TemplateDirectory.findProceduresForCopy` (te same filtry co podgląd karty szablonu: proces raz, w kolejności pierwszego wystąpienia) i zapisuje je transakcją tworzenia zlecenia. Plan (`domain/composition-plan.ts`) numeruje pozycje od 1 i wskazuje pozycję zakresu, która proces wniosła (`source_scope_item_id`); przekroczenie limitu 30 procesów / 30 etapów to wyjątek (cofnięcie całości, bez przycinania). Zlecenia sprzed EVM-031 nie mają procesów (bez backfillu).
- **Kolejność w transakcji** (`application/update-stage.service.ts`, komentarz na górze pliku): ścieżka → `Idempotency-Key` i `If-Match` (przed bazą) → zlecenie `FOR UPDATE` (`404`) → etap `FOR UPDATE` z `id` **i** `work_order_id` w jednym warunku (`404`) → treść (`400`) → idempotencja → `409 work_order_closed` → `412` → osoba (`UserDirectory.findActive`, `400 assignee_unavailable`) → zapis, audyt, rekord idempotencji. Pola serwera (`status`, `name`, `version`, `notes`, „czekamy na” …) to `read_only_field`.
- **Dane:** `ProcedureStage.responsibleUserId` (DO-P) wychodzi wyłącznie jako `{ id, displayName }`; odczyt nie zwraca notatek, „czekamy na” ani powodu blokady. Nazwy osób — partiami po 100 (`responsible-names.ts`). Audyt zawiera aktora i etap (identyfikator zlecenia wynika z etapu), bez wartości.
- **Dzień „dziś”:** `platform/clock/business-date.ts` (`Europe/Warsaw`, jedna implementacja z `work-orders`); `overdue` = termin < dziś i status poza `done` / `not_applicable` (etap `blocked` po terminie jest spóźniony).
- **Migracja `0019_procedures`** (expand): schemat `procedures`; złożony klucz `(procedure_id, work_order_id)` do `procedures (id, work_order_id)`; jeden aktywny proces na kod i pozycję w zleceniu, jeden aktywny etap na kod i pozycję w procesie; `status` `text` + CHECK, domyślnie `todo`; `due_date` 2000-01-01..2100-12-31; wszystkie klucze `ON DELETE RESTRICT`; rola aplikacji ma `SELECT`, `INSERT`, `UPDATE` (bez `DELETE`).
- **Dług / uwagi:** zlecenie z ponad 100 różnymi osobami odpowiedzialnymi działa (partie), ale każda partia to osobne zapytanie; `findActive` nie blokuje konta (`FOR SHARE`) — przy równoległej dezaktywacji etap może dostać osobę dezaktywowaną chwilę wcześniej (przypisanie nie nadaje uprawnień); odczyt procesów nie wlicza się do licznika masowego odczytu (P10) — do ponownej oceny w EVM-032 (notatki, „czekamy na”).

## Dziennik zlecenia (moduł `timeline`, EVM-037)
- **Operacje:** `listTimelineEntries` (`GET /api/v1/work-orders/{workOrderId}/timeline`; A / E / R, kanał `web`), `getTimelineEntry` (`…/timeline/{entryId}`; A / E / R) i `createTimelineEntry` (`POST …/timeline`; A / E, kanał `web`, audyt `timeline_entry.created` bez treści; `Idempotency-Key` wymagany). - **Kolejność w transakcji** (`application/create-entry.service.ts`, komentarz na górze pliku): ścieżka → zlecenie (`404`) → nagłówek i treść (`400`) → powtórka idempotentna → etap → poprawiany wpis (`FOR UPDATE`) → `INSERT` (`id_conflict`, zmapowane naruszenia ograniczeń) → zdarzenie audytu i rekord idempotencji. Klucz idempotencji jest związany ze zleceniem (`createTimelineEntryScope`).
- **Treść:** `domain/entry-body.ts` — jedna funkcja na granicy (NFC, CRLF → LF, usunięcie C0 / C1 i znaków kierunku tekstu, przycięcie, 1–10 000 punktów kodowych po normalizacji, samotny surogat → `invalid_characters`); reguły wpisu (kategoria tylko dla `note`): `domain/create-entry-rules.ts`. Treść nigdy nie trafia do audytu, logów, błędów ani rekordu idempotencji.

- **Migracja `0020_timeline`** (expand): schemat `timeline`, tabela `timeline_entries`; klucze złożone `(procedure_stage_id, work_order_id)` i `(supersedes_entry_id, work_order_id, kind)`; UNIQUE `supersedes_entry_id` (wpis poprawiany najwyżej raz); wyzwalacz odrzuca zmianę każdej kolumny poza `deleted_at`, `deleted_by` i `version`; rola aplikacji ma `SELECT`, `INSERT`, `UPDATE` (bez `DELETE` i `TRUNCATE`). Dodaje też UNIQUE `(id, work_order_id)` na etapach procesów.
- **Limit ciała:** trasa `POST …/timeline` przyjmuje do 64 KB (`ROUTE_BODY_LIMITS` w `src/app.ts`, `413 payload_too_large`); pozostałe trasy sesji — 1 MB.
- **Dług / uwagi:** audyt ma stały zestaw kolumn, więc zlecenie, rodzaj i poprawiany wpis czyta się z samego wpisu po `objectId`; zdarzenia dziennika (`kind = event`, EVM-038) oraz usunięcie i redakcja (EVM-040) dopiero powstaną — trigger zostanie wtedy poluzowany dla `redacted_*` i treści.

## Konfiguracja
**Które polecenie wymaga `CURSOR_KEY`** (EVM-080): serwer API (`start`, `dist/src/main.js`), worker (`worker` / `start:worker`) i polecenia CLI (`admin:activate`, `overview`, `process-run`) — **tak**, wczytują pełną konfigurację (`loadConfig`) i bez poprawnego klucza kończą się błędem konfiguracji, który wymienia tylko nazwę zmiennej (`CURSOR_KEY`), nigdy wartość; `db:migrate` — **nie** (`loadMigrationConfig`, wyłącznie `DATABASE_URL`, `NODE_ENV`, `LOG_LEVEL`). **Zmiana (rotacja) `CURSOR_KEY` unieważnia wszystkie wydane kursory** (do 30 minut ich życia): klient dostaje `400 invalid_cursor`, panel pokazuje komunikat o odświeżeniu listy i wraca na pierwszą stronę; nie ma migracji danych. Worker i CLI nadal wymagają klucza — to osobny dług (EVM-024).

**E-mail transakcyjny — tylko worker** (EVM-024): `EMAIL_TRANSPORT` (`smtp` | `none`, wymagany, bez wartości domyślnej), `EMAIL_SMTP_HOST` (tylko `mailpit`, `localhost`, `127.0.0.1`, `::1`), `EMAIL_SMTP_PORT`, `EMAIL_FROM` (sam adres) — wczytuje je wyłącznie `loadWorkerConfig` (worker); serwer API i polecenia CLI ich nie czytają (API nie wysyła poczty, więc jego start ich nie wymaga). `smtp` przy `NODE_ENV=production` (także gdy `NODE_ENV` nie ustawiono) to błąd startu; `none` jest jawne w każdym środowisku (worker niczego nie wysyła, wiersze skrzynki czekają, healthcheck czerwony). Link w e-mailu budowany z `PANEL_ORIGIN` (nigdy z `Host`). Kolejka, skrzynka i runbook: `docs/ops/runbooks/kolejka-e-mail.md`.

Zmienne i przykłady: `.env.example` (`DATABASE_URL`, `API_PORT`, `LOG_LEVEL`, `NODE_ENV`, `MIN_SUPPORTED_APP_VERSION_ANDROID`, `MIN_SUPPORTED_APP_VERSION_IOS`, `PANEL_ORIGIN`, `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME`, `TRUSTED_PROXIES`, `CURSOR_KEY` — wymagany, 32 bajty base64url, `FIELD_ENCRYPTION_KEYS` — wymagany w produkcji, lista `id:klucz`, klucz 32 bajty base64url; EVM-023). `LOG_LEVEL` `debug`/`trace` tylko przy `NODE_ENV=development`.
