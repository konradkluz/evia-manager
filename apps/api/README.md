# `@evia/api` — API EVia Manager (NestJS)

Szkielet z EVM-008 (AC1, AC2, AC4; ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0013). Modularny monolit NestJS 12 (Express 5), PostgreSQL przez Kysely, kontrakt z `@evia/contracts`.

|---|---|
| `pnpm --filter @evia/api run build` | `tsc` → `dist/` (NestJS wymaga dekoratorów, których Node nie usuwa) |
| `pnpm --filter @evia/api run start` | `node dist/src/main.js` — wymaga zmiennych z `.env.example` |
| `pnpm --filter @evia/api run db:migrate` | migracje „w przód” (Kysely `Migrator`); nigdy przy starcie API |

| `pnpm --filter @evia/api run test:integration` | testy z PostgreSQL: Testcontainers (CI, job `backend-integration`) albo baza z `EVIA_TEST_DATABASE_URL`; mierzy kod związany z bazą (`coverage.config.ts`) z progiem 85% — API łączy się tu rolą `evia_app` (członek roli, nie właściciel), więc brak `GRANT` wychodzi w testach |

## Autoryzacja (deny-by-default)
Każdy handler ma `@OperationId('<operationId z kontraktu>')`; polityka pochodzi wyłącznie z manifestu `@evia/contracts/authz`:
Kolejność kontroli jest stała (szczegóły: `docs/architecture/api-guidelines.md` → Autoryzacja): manifest → operacja publiczna (Origin + Sec-Fetch-Site + limit) → sesja → CSRF → limit logowania i MFA → stan `mfa_enrollment` → kanał → rola → step-up (`403 step_up_required`, tylko operacje z `stepUp: true`) → polityka obiektowa w przypadku użycia (`404`).
1. brak `operationId` lub polityki w manifeście → `403 forbidden` (a przy starcie — błąd: aplikacja nie wstaje, gdy trasa nie ma polityki albo „pożycza” operację o innej metodzie lub ścieżce);
2. `x-evia-authz: { public: true }` → przepuszczone tylko dla operacji z `PUBLIC_OPERATIONS` (dziś `getHealth`, `checkActivationLink`, `setActivationPassword`, `login`, `getLoginPasskeyOptions`, `verifyLoginPasskey`);
3. brak sesji → `401 unauthenticated` (sesja unieważniona → `401 session_revoked`, sesja, której minął czas → `401 session_expired`); nieistniejąca trasa bez sesji też `401` (bez ujawniania mapy tras);
4. mutacja sesji bez poprawnego `Origin`, `Sec-Fetch-Site` i `X-CSRF-Token` → `403 csrf_failed`; sesja `mfa_enrollment` poza operacjami z `MFA_ENROLLMENT_OPERATIONS` → `403 mfa_enrollment_required`; rola lub kanał spoza polityki → `403 forbidden`.
Testy macierzy ról są generowane z kontraktu (`test/authorization/role-matrix.ts`): każda operacja × Administrator / Edytor / Tylko odczyt × `web` / `mobile` × stan sesji + niezalogowany + unieważniona i wygasła sesja, przypadek IDOR dla operacji z parametrem ścieżki, test kompletności i test testu z „dziurawą” polityką.

## Logowanie i sesje (moduł `identity`, EVM-067)
Dwa kroki, wszystkie operacje publiczne, kanał `web` nadaje ścieżka (nie klient). Wartości i mechanizmy (ASVS V6.1.1, V7.1.1):

| Co | Wartość | Gdzie |
|---|---|---|
| bezczynność sesji | **60 min** od ostatniej aktywności | `SESSION_IDLE_MS` (`domain/constants.ts`) |
| limit bezwzględny sesji | **12 h** od zalogowania, nie przesuwa się | `SESSION_ABSOLUTE_MS` |
| zapis aktywności | co najwyżej co 30 s; odczyt sesji (`getCurrentSession`) i `extendSession` nie są aktywnością | `SESSION_TOUCH_INTERVAL_MS`, `PASSIVE_OPERATIONS` |
| `loginToken` (pierwszy krok) | 256 bitów, w bazie tylko SHA-256, **5 min**, jednorazowy, maks. 5 nieudanych kluczy | `LOGIN_ATTEMPT_TTL_MS`, `LOGIN_MAX_FAILED_PASSKEYS` |
| wyzwanie WebAuthn | ≥ 128 bitów (256), w bazie SHA-256, **5 min**, jednorazowe; zużywane przy każdej weryfikacji, nowe opcje unieważniają poprzednie | `CHALLENGE_TTL_MS` |
| wiersze prób logowania | usuwane przy następnym pierwszym kroku, najpóźniej 24 h po wygaśnięciu; brak adresu IP i user agenta w tabeli (RODO — dane klienta tylko w sesji i prefiks w audycie) | `LOGIN_ATTEMPT_RETENTION_MS`, migracja `0006` |
| limit prób | 20 na minutę z jednego IP dla `login`, `getLoginPasskeyOptions`, `verifyLoginPasskey` (wspólny), liczony w guardzie przed dostępem do bazy; IP tylko z `request.ip` (`TRUSTED_PROXIES`), nigdy z surowego `X-Forwarded-For`; `429 rate_limited` z `Retry-After` | `AUTHENTICATION_OPERATIONS`, `platform/http/rate-limiter.ts` |

- **Jednakowe odpowiedzi (SR-AUTH-05):** zły e-mail, złe hasło, konto zaproszone i dezaktywowane → ten sam `401 invalid_credentials` (kod, treść, nagłówki) i dokładnie jedna weryfikacja Argon2id — dla konta aktywnego względem jego hasha, w pozostałych przypadkach względem hasha-wabika wygenerowanego przy starcie bieżącymi `ARGON2_PARAMETERS` i weryfikowanego tą samą ścieżką `verify`. Hasło jest normalizowane do NFC (jak przy aktywacji), bez przycinania i zmiany wielkości liter; polityka długości nie obowiązuje przy logowaniu, schemat sprawdza kształt (e-mail ≤ 254, hasło ≤ 1024). Powód porażki trafia tylko do audytu (`login.failed`: `bad_password`, `unknown_user`, `not_active`, `passkey_failed`, `login_expired`; bez hasła, e-maila i jego skrótu) i do metryki `evia_login_failures_total{reason}` (`platform/metrics`; wystawienie do Prometheusa — EVM-007).
- **Drugi krok (SR-AUTH-09):** klucz szukany po `credential_id` **i** koncie z `loginToken` (klucz innego konta = `401 passkey_failed`), `userHandle` musi być kontem, `allowCredentials` tylko z jego kluczami, `userVerification: required`, origin i RP ID z konfiguracji. Sukces w jednej transakcji: atomowe zużycie wyzwania i `loginToken`, ponowna kontrola `users.status` pod blokadą `FOR SHARE`, licznik i `last_used_at` klucza, `lastLoginAt`, nowa sesja (token z CSPRNG), unieważnienie sesji z ciasteczka żądania (`rotated`; przy podwójnym ciasteczku nic) i audyt `login.succeeded`. Dwa równoległe żądania z tą samą asercją dają jedną sesję.
- **Step-up i dziennik audytu (EVM-029; SR-SESS-08, SR-SESS-02):** operacja z `stepUp: true` wymaga uwierzytelnienia kluczem w sesji w ciągu 15 minut (`passkey_authenticated_at`, zegar wstrzykiwany; po roli i kanale, więc E i R dostają `forbidden`); `getStepUpPasskeyOptions` i `stepUp` (limit 20/min/IP): wyzwanie o celu `passkey_step_up` powiązane z sesją, asercja tym samym kodem co logowanie (`passkey-assertion.ts`), sukces w jednej transakcji — warunkowy `UPDATE` kończy sesję (`rotated`), nowa sesja z nowym tokenem i CSRF, limit 12 h bez zmian; porażka → `401 passkey_failed` i `step_up.failed`, sesja bez zmian. `listAuditEvents`: kursor `(occurred_at, id)`, jawna lista kolumn, `audit.read` w tej samej transakcji (fail closed), nazwy osób przez fasadę `UserDirectory.displayNamesOf`.
- **Wygasanie (SR-SESS-03):** wszystkie stany sesji (`active`, `mfa_enrollment` z linkiem i bez); kolejność: unieważniona → wygasła → dopiero potem przesunięcie bezczynności warunkowym `UPDATE` (wygasła sesja nie wraca). Wygasła sesja: `401 session_expired`, `session.expired` w audycie dokładnie raz (`revoke_reason = 'expired'`). Czas rzeczywisty z wstrzykiwanego zegara.
- **Sesja `mfa_enrollment` po samym haśle** (konto aktywne bez klucza): bez linku, nie może zarejestrować czynnika (`registerPasskey` odrzucone); rejestracja czynnika po samym haśle — EVM-023 / SR-AUTH-13.

## Katalog i szablony (moduł `catalog`, EVM-019)
- **Dane startowe** to migracja danych `0008_catalog_seed` (schemat `0007_catalog`) z zamrożonej kopii `src/migrations/data/catalog-seed-2026-10.ts` wg `docs/product/service-catalog.md`: 12 pozycji katalogu, 10 szablonów procesów (32 etapy), 16 rodzajów dokumentów, 5 szablonów zleceń (26 pozycji, 11 transz). Zmiana danych = **nowa migracja danych z własną zamrożoną kopią** (nigdy edycja starej); migracje nie czytają zegara bazy (stały znacznik czasu w danych) i wstawiają wartości tylko jako parametry.
- **Tylko do odczytu:** rola `evia_app` ma `USAGE` na schemacie i jawne `SELECT` na każdej tabeli, nic więcej (bez `ALTER DEFAULT PRIVILEGES`); kontrakt nie ma operacji `POST`/`PUT`/`PATCH`/`DELETE` w `/api/v1/catalog` (edytor — M4). Testowe wycofanie szablonu (`is_active = false`) robi rola migracyjna.
- **Operacje** (wszystkie `GET`, role Administrator / Edytor / Tylko odczyt, kanał `web`, bez audytu — odczyt konfiguracji nie jest zdarzeniem wrażliwym): `listWorkOrderTemplates` (`?siteTypeHint=`, tylko aktywne), `getWorkOrderTemplate` (po `templateId`, także wycofany; nieznany → `404 not_found`, zły format → `400 validation_failed`), `listServiceItems`, `listProcedureTemplates`, `listDocumentKinds`. Zbiory są małe i zwracane w całości w kopercie `{ items, nextCursor: null }` (≤ 100 elementów — pilnuje test spójności); `limit` i `cursor` nie są deklarowane (→ `400 unknown_parameter`) do czasu edytora w M4. Odpowiedź jest walidowana schematem kontraktu, a nagłówek to wyłącznie globalne `Cache-Control: no-store`. Procesy podglądu szablonu to procesy wnoszone przez jego pozycje (współdzielony proces — raz).
- **Zestawy parametrów** (`domain/parameter-sets.ts`): `charger_spec`, `charger_installation`, `supply_circuit`, `connection_power`, `dso_request` — ścisłe (bez pól dodatkowych, także `__proto__`), zakresy liczb, tekst NFC bez znaków sterujących, ≤ 16 KB JSON-a w bajtach UTF-8 (to samo `octet_length` w CHECK kolumny `default_parameters`). Widok `defaults` (pola opcjonalne) dla pozycji szablonu, `full` dla pozycji zlecenia (EVM-022).
- **Spójność konfiguracji** (`domain/config-consistency.ts`, `validateCatalogConfig`): suma udziałów = 100, wzorzec kodu `^[a-z][a-z0-9_]{1,63}$`, nieznany `parameterSetCode`, etap z nieistniejącym rodzajem dokumentu, wartości domyślne względem schematu itd.; błąd wskazuje kod elementu. Uruchamiany w bramce (test na danych startowych i na danych odczytanych z bazy).

## Zlecenia — lista (moduł `work-orders`, EVM-017)
- **Operacja:** `listWorkOrders` (`GET /api/v1/work-orders`; Administrator / Edytor / Tylko odczyt, kanał `web`, bez audytu odczytu). Schemat `work_orders` (migracja `0010`): `work_orders` (numer `COLLATE "C"`, tytuł, status z CHECK) i `work_order_assignments` (`coordinator` — co najwyżej jeden aktywny — i `technician`; „aktywne” = `deleted_at IS NULL`); `evia_app` ma `SELECT`, `INSERT`, `UPDATE` (soft delete, bez `DELETE`). Klucze obce do klientów i lokalizacji dodaje EVM-022.
- **Zapytanie:** filtry łączą się przez AND — `status` (lista po przecinku, ścisły enum, zbiór normalizowany), `view` (`all_open` albo `mine`; brak = bez predykatu widoku, domyślny widok wybiera panel), `coordinatorId`; `sort`: `-number` (domyślne), `number`, `-createdAt`, `createdAt`; `limit` 1–100 (domyślnie 25). `mine` bierze użytkownika wyłącznie z sesji. ORDER BY i porównanie keyset pochodzą z mapy enum → kolumna (`SORT_RULES`), nigdy z wartości żądania; jedno zapytanie (LEFT JOIN do aktywnego opiekuna, `LIMIT n+1`) i jedno wsadowe `UserDirectory.displayNamesOf`.
- **Polityka odczytu jest warunkiem zapytania:** `visibleWorkOrders(principal)` (`infrastructure/read-policy.ts`) — dziś `deleted_at IS NULL` dla każdej roli (także Administratora; widok usuniętych — EVM-060); użyją jej kolejne operacje (szczegóły, wyszukiwanie, synchronizacja).
- **Kursor** (`platform/crypto/opaque-cursor.ts`): AES-256-GCM z `node:crypto`, losowy 96-bitowy nonce, bajt wersji i identyfikator operacji jako AAD, ładunek: pozycja, skrót znormalizowanych filtrów (z `sort`; bez `limit`), `userId`, wygaśnięcie (30 min). Każdy błąd (zmiana, inne filtry, inny użytkownik, wygaśnięcie, inna operacja) to jedno `400 invalid_cursor`. Wartości po odszyfrowaniu są walidowane ponownie. Klucz `CURSOR_KEY` (32 bajty base64url, wymagany w każdym środowisku; produkcja odrzuca zaślepkę); **rotacja klucza unieważnia kursory** — panel wraca na pierwszą stronę.
- **Masowy odczyt (P10, RR-13)** (`platform/bulk-read`): licznik rekordów zwróconych użytkownikowi w oknie 10 minut (kubełki minutowe). Sprawdzenie PRZED zapytaniem, doliczenie zwróconych rekordów PO; żądanie odrzucone albo błędne nic nie dolicza. Od 2000 rekordów jeden alert na okno i użytkownika — wpis w logu procesu API (`alert: "security"`, `alertCode: "bulk_read"`, `traceId`; bez użytkownika, tytułów i wartości filtrów) i liczniki `bulk_read_alert`, `bulk_read_rejected` bez etykiet; osobę wskazuje wyłącznie dziennik audytu — pierwszy alert i pierwsze odrzucenie `429` w oknie zapisują zdarzenia `bulk_read.alerted` / `bulk_read.rejected` (aktor, sesja, `traceId`, obiekt `work_order`; bez wartości filtrów, tytułów i liczby rekordów), publikowane przez dispatcher `platform/events`, który subskrybuje `audit`; od 10 000 `429 rate_limited` z `Retry-After` (sekundy do chwili, gdy suma spadnie poniżej progu). Progi są wstrzykiwane przez DI (`BULK_READ_LIMITS`; testy podmieniają dostawcę), konfiguracja ich nie wyłącza. **Ograniczenie:** stan jest w pamięci jednego procesu API (jak limiter per IP) — restart zeruje liczniki (ryzyko rezydualne, niskie); przy replikacji API implementacja w PostgreSQL za tym samym portem (`BulkReadMeter`). **Różni klienci (EVM-039, P10 pkt 5a):** `DistinctReadMeter` (`distinct-read-meter.ts`) liczy RÓŻNE identyfikatory klientów odczytanych przez użytkownika (nie sesję) w oknie przesuwnym 60 minut; alert (`alert: "security"`, `alertCode: "bulk_read_customers"`, bez użytkownika i identyfikatorów; audyt `bulk_read.alerted` z obiektem `customer`) przy 301. różnym kliencie, raz na okno. Zasilają go lista, wyszukiwanie, szczegóły i karta „Klient” zlecenia (`BulkReadControl.afterDistinct`, po zbudowaniu odpowiedzi 2xx). Pamięć: najwyżej 301 identyfikatorów na użytkownika i `MAX_TRACKED_DISTINCT_USERS` użytkowników; przy przepełnieniu najpierw znikają bezczynni, potem najdawniej aktywny (aktywny użytkownik nie traci licznika). Restart zeruje licznik (to samo zaakceptowane ryzyko).
- **Dane testowe:** generator 10 000 syntetycznych zleceń to pomocnik testów (`test/support/work-order-fixtures.ts`, poza obrazem produkcyjnym; odmawia przy `NODE_ENV=production`). Numery `ZL-RRRR-NNNN` mają stałą szerokość (do 9999 na rok), więc generator rozkłada zlecenia na kilka lat.

## Klienci — wyszukiwanie, dodanie, lista, szczegóły i edycja (moduł `customers`, EVM-020, EVM-039)
- **Lista, szczegóły, edycja (EVM-039):** `listCustomers` (`GET /api/v1/customers`), `getCustomer` (`GET …/{customerId}`, `ETag`), `updateCustomer` (`PATCH …/{customerId}`; A / E). Strona listy i wyszukiwania to jedna usługa (`CustomerPagesService`): kursor (`CURSOR_CODEC`, operacja + użytkownik + skrót frazy) zawiera tylko `id` ostatniego klienta, klucz sortowania czyta czytnik (`customer-list-reader.ts`: `(sort_name, id) > (…)` po indeksie `customers_sort_name_id_idx`, migracja `0017`). Edycja: `If-Match` i treść (kształt) przed bazą, potem jedna transakcja z `SELECT … FOR UPDATE` (polityka odczytu w zapytaniu → `404`), idempotencja z zakresem zawierającym `id` klienta, wersja (`412`), `mergeCustomerPatch` + ta sama `normalizeNewCustomer` co przy dodaniu, `UPDATE … version + 1`, zdarzenie `customer.updated` (bez pól i wartości). Historia zleceń to filtr `customerId` listy zleceń (indeks `work_orders_customer_created_idx`).
- **Operacje:** `searchCustomers` (`POST /api/v1/customers/search`; A / E / R) i `createCustomer` (`POST /api/v1/customers`; A / E), kanał `web`. Schemat `customers` (migracja `0011`): `customers` z `id` UUIDv7 nadawanym przez klienta (CHECK `uuid_extract_version(id) = 7`, bez domyślnej wartości), adresem w pięciu kolumnach, kolumnami generowanymi `display_name`, `sort_name` i `search_text` (`f_unaccent(lower(…))`: imię, nazwisko, firma, NIP, cyfry telefonu, e-mail, miasto — bez notatek i osoby kontaktowej) i częściowym indeksem GIN `gin_trgm_ops` (`deleted_at IS NULL`); `evia_app` ma `SELECT`, `INSERT`, `UPDATE`.
- **Kolejność w wyszukiwaniu:** guard (401 → 403 → CSRF) → limit 60/min/użytkownika (`RateLimiter.consumeSubject`; klucz to identyfikator użytkownika, nie adres IP) → walidacja treści i frazy → otwarcie kursora (`400`) → `BulkReadControl.before(…, 'customer')` → zapytanie z twardym `LIMIT` (domyślnie 25, najwyżej 100, plus jeden wiersz na wykrycie następnej strony) → `after` i `afterDistinct`. Fraza jest escapowana (`%`, `_`, ukośnik odwrotny) i porównywana `ILIKE … ESCAPE` z parametrem; nigdy nie trafia do logów, metryk ani `errors[]`.
- **Dodanie klienta:** treść ścisła (pola serwera → `read_only_field`, lista z różnicy `zCustomer` i `zCustomerWritable`), reguły rodzaju w domenie (`domain/customer.ts`: telefon E.164 bez biblioteki, NIP z sumą kontrolną, e-mail, zwykły tekst NFC), `INSERT … ON CONFLICT (id) DO NOTHING` (zajęte `id` → `409 id_conflict`, także usuniętego klienta), zdarzenie `customer.created` w tej samej transakcji.
- **Idempotencja** (`platform/idempotency`, migracja `0012`): port `Idempotency.run(tx, żądanie, operacja)` wołany w jednostce pracy serwisu; `pg_try_advisory_xact_lock` → `409 idempotency_in_progress` (`Retry-After: 1`), rekord (`scope`, skrót SHA-256 kanonicznego JSON-a, wynik minimalny 2xx, 30 dni) zapisany w tej samej transakcji; powtórka zwraca bieżącą reprezentację z `Idempotent-Replayed: true`; inny skrót lub zakres → `422 idempotency_mismatch` (metryka). Czyszczenie wygasłych rekordów — dług (job pg-boss); do tego czasu odczyt filtruje po `expires_at`, a wygasły rekord jest nadpisywany. Metryki: `idempotency_mismatch`, `idempotency_in_progress`, `customer_search_rate_limited`.

## Lokalizacje i strony — wyszukiwanie i dodanie (moduły `sites` i `parties`, EVM-021)
- **Operacje:** `searchSites` (`POST /api/v1/sites/search`), `createSite` (`POST /api/v1/sites`), `searchParties` (`POST /api/v1/parties/search`), `createParty` (`POST /api/v1/parties`); wyszukiwanie A / E / R, utworzenie A / E, kanał `web`. Schematy `parties` (migracja `0013`) i `sites` (`0014`): `id` UUIDv7 nadawany przez klienta (CHECK, bez wartości domyślnej), kolumny generowane `search_text` (strony: nazwa i osoba kontaktowa; lokalizacje: adres i numer miejsca — bez PPE i notatek) i częściowe indeksy GIN `gin_trgm_ops` (`deleted_at IS NULL`); CHECK-i: miejsce i poziom tylko dla `multi_family_garage`, kod `NN-NNN`, moc `numeric(6,2)` w (0, 1000] kW, PPE ≤ 40; klucze obce `sites` → `parties` z `ON DELETE RESTRICT`; `evia_app` ma `SELECT`, `INSERT`, `UPDATE` (bez `DELETE`).
- **Kierunek zależności:** `sites` → `parties` wyłącznie przez `index.ts` (fasada `PartyDirectory.kindsOf(tx, principal, ids)`); `customers` nie jest dotykany (lokalizacja nie zna klienta — D7). Wspólne reguły tekstu, telefonu, e-maila, frazy i dopasowania `search_text` (`searchTextMatches`: normalizacja w SQL, ucieczka znaków wzorca LIKE PO normalizacji) są w `platform/input` i `platform/database`.
- **Wyszukiwanie:** guard → limit 60/min/użytkownika w osobnym kubełku (`search-sites`, `search-parties`) → walidacja treści i frazy (dla stron także `kinds`) → `BulkReadControl.before(…, 'site' | 'party')` → zapytanie z `LIMIT 20` → `after`. Wynik bez notatek, PPE, mocy i stron (lokalizacje) oraz bez telefonu, e-maila i osoby kontaktowej (strony).
- **Dodanie lokalizacji:** treść ścisła (pola serwera → `read_only_field`, `customerId` → `unknown_field`), reguły w domenie (`domain/site.ts`: garaż, skala mocy, tekst NFC, kod pocztowy), a w jednej transakcji z `INSERT`: rodzaj stron z pól `…PartyId` (`wrong_party_kind`, `unknown_party` — ten sam kod dla strony usuniętej i nieistniejącej). Rekord idempotencji powstaje dopiero po tych kontrolach (błąd cofa transakcję), zdarzenia `site.created` / `party.created` zawierają tylko identyfikatory.
- **Dług / uwagi:** wyścig między sprawdzeniem strony a jej soft delete — przy edycji lokalizacji (EVM-036) wiersze stron są czytane `FOR SHARE` w transakcji zapisu, przy tworzeniu (EVM-021) nadal bez blokady (do rozważenia z EVM-060); zakres mocy 0 < kW ≤ 1000 to założenie do potwierdzenia przez właściciela produktu.

## Edycja lokalizacji i stron, inne zlecenia w lokalizacji (moduły `sites`, `parties` i `work-orders`, EVM-036)
- **Operacje:** `getSite` / `updateSite` (`GET`, `PATCH /api/v1/sites/{siteId}`), `getParty` / `updateParty` (`GET`, `PATCH /api/v1/parties/{partyId}`), `listWorkOrderSiteOrders` (`GET /api/v1/work-orders/{workOrderId}/site-orders`); odczyt A / E / R, edycja A / E, kanał `web` (token mobilny — `403`; sekcja „inne zlecenia” jest tylko w panelu, SR-AUTHZ-08). Bez migracji danych; migracja `0018` dodaje częściowy indeks `work_orders_site_number_idx (site_id, number desc, id desc)`.
- **Edycja (`UpdateSiteService`, `UpdatePartyService`):** wzór `UpdateCustomerService` — `If-Match` i treść (kształt) przed bazą, potem jedna transakcja: `SELECT … FOR UPDATE` z polityką odczytu w zapytaniu (brak albo usunięty zasób — `404`, także ze starym `If-Match`) → idempotencja (klucz związany z `siteId` / `partyId`) → wersja (`412`) → merge-patch przez reguły tworzenia (`site-patch.ts`, `party-patch.ts`; `null` czyści pole opcjonalne; zmiana typu z garażu wymaga wyczyszczenia miejsca i poziomu w tym samym żądaniu) → kontrola rodzaju stron OSD i zarządcy **tylko dla pól wskazanych w treści** (`PartyDirectory.kindsOf(…, { lock: true })` czyta wiersze `FOR SHARE` w tej samej transakcji; błąd bez wartości i bez faktycznego rodzaju) → `UPDATE … WHERE id AND version` (`version + 1`) → zdarzenie `site.updated` / `party.updated` (aktor, identyfikator; bez nazw pól i wartości). Rodzaj strony jest niezmienny — `PartyPatch` nie ma `kind` (`read_only_field`).
- **Inne zlecenia (`ListSiteOrdersService`):** zlecenie rozwiązywane najpierw przez `visibleWorkOrders` (brak albo usunięte — `404`); `site_id` pochodzi z tego wiersza, ścieżka nie ma parametru `siteId`, a parametry zapytania są odrzucane (`400`). Jedno zapytanie (`site-orders-reader.ts`) zwraca najwyżej 20 pozycji (numer malejąco) i `count(*) over ()` z tym samym warunkiem `visibleWorkOrders` i `id <> :id`; kolumny jawne, bez JOIN do klientów, mediów, dokumentów i płatności. Zlecenia usunięte nie występują nigdzie (także dla Administratora — podgląd usuniętych to EVM-060).
- **Dług / uwagi:** nazwy zmienionych pól nie trafiają do audytu (wzorem `customer.updated`; kandydat do backlogu); tytuł zlecenia w „innych zleceniach” jest polem swobodnym i może zawierać dane osobowe (RR-13, ponowna ocena przy M3 i M4).

## Nowe zlecenie z szablonu (moduł `work-orders`, EVM-022)
- **Operacje:** `createWorkOrder` (`POST /api/v1/work-orders`; A / E, kanał `web`, audyt `work_order.created`) i `listAssignableUsers` (`GET /api/v1/users/assignable`, moduł `identity`; A / E, bez parametrów, najwyżej 100 aktywnych użytkowników, tylko `id` i `displayName`). Guard (401 → 403 → CSRF) działa przed walidacją i idempotencją, więc Tylko odczyt dostaje `403` dla każdej treści i nie zapisuje rekordu idempotencji.
- **Kierunek zależności:** `work-orders` → `customers` (`CUSTOMER_DIRECTORY`), `sites` (`SITE_DIRECTORY`), `catalog` (`TEMPLATE_DIRECTORY`), `identity` (`UserDirectory.findActive`, `displayNamesOf`) wyłącznie przez `index.ts`; każda fasada dostaje transakcję wywołującego (kontrola i zapis to jedna jednostka pracy) i stosuje politykę odczytu (`deleted_at IS NULL` dla każdej roli — usunięty obiekt jest tak samo nieznany jak nieistniejący).
- **Kolejność w transakcji** (`application/create-work-order.service.ts`): idempotencja (gdy jest klucz) → klient, lokalizacja (`404`) → szablon (`422 template_unavailable`) → opiekun (`400 assignee_unavailable`, jeden kod dla konta nieistniejącego, zaproszonego, dezaktywowanego i usuniętego) → numer z licznika i `INSERT` zlecenia (`409 id_conflict` przy istniejącym `id`, także usuniętym zleceniu) → pozycje zakresu (kopia, D1) → przypisanie `coordinator` → kontrybutorzy → zdarzenie audytu → odczyt zlecenia (też przy powtórce, uprawnieniami wywołującego). Każdy wyjątek cofa całość: brak zlecenia, pozycji, przypisania, wpisu audytu i rekordu idempotencji; numer nie jest zużyty.
- **Numer** (`infrastructure/number-counter.ts`, tabela `work_orders.number_counters`): `INSERT … ON CONFLICT (year) DO UPDATE SET last_value = last_value + 1 RETURNING` w transakcji tworzenia — nie sekwencja (sekwencja nie jest cofana, powstałaby luka); blokada wiersza liczy tworzenia po kolei do zatwierdzenia. Rok to rok w `Europe/Warsaw` z wstrzykiwanego zegara (`domain/work-order-number.ts`). Format `ZL-RRRR-NNNN` (co najmniej 4 cyfry; sortowanie bajtowe jest poprawne do 9999 zleceń rocznie — 0010).
- **Port `WorkOrderCompositionContributor`** (`composition-contributor.ts`, rejestr `WorkOrderCompositionRegistry` eksportowany z modułu): implementacje (`procedures` — EVM-031, `payments` — EVM-053) rejestrują się same; kolejność stała (`order`, potem `name`), ta sama transakcja, **bez zewnętrznego I/O** (żadnych wywołań HTTP w transakcji), błąd cofa całość. Teraz nie ma implementacji.
- **Dane:** tytuł domyślny to nazwa szablonu albo „Nowe zlecenie”; `description` do 2000 znaków, `title` do 200, zwykły tekst NFC; `plannedDate` `RRRR-MM-DD` z zakresu 2000-01-01 … 2100-12-31 (`out_of_range`). `ScopeItem.parameters` to kopia wartości technicznych szablonu (JSONB ≤ 16 KB, CHECK w bazie). Audyt `work_order.created` niesie tylko identyfikatory; tytuł i opis nie trafiają do logów, błędów ani audytu.
- **Migracja `0015_work_order_creation`** (expand): kolumny `customer_id`, `site_id`, `source_template_id` (klucze obce `ON DELETE RESTRICT`; w bazie nullable — zlecenie z terenu uzupełnia się później, API ich wymaga), `planned_date`, `description`, CHECK numeru `^ZL-[0-9]{4}-[0-9]{4,}$` i identyfikatora (UUIDv7), tabele `scope_items` (pozycje zakresu skopiowane z szablonu) i `number_counters` (licznik roczny); `evia_app` ma `select`, `insert`, `update` na obu tabelach, bez `delete`.

## Cykl życia zlecenia (moduł `work-orders`, EVM-030)
- **Operacja:** `transitionWorkOrder` (`POST /api/v1/work-orders/{workOrderId}/transitions`; A / E, kanał `web`, audyt `work_order.cancelled` i `work_order.restored`; `If-Match` wymagany, `Idempotency-Key` opcjonalny). Odczyt szczegółów (`getWorkOrder`) dostał `allowedTransitions` (cele dozwolone dla roli wołającego: Tylko odczyt — pusta lista, Edytor bez przywróceń), `resumeStatus`, `statusChangedAt`, `closedAt`, `completedOn`.
- **Tabela przejść** (`domain/work-order-transitions.ts`): jedyne miejsce, które mówi, co może po czym, dla kogo i z jakim skutkiem (z `domain-model.md` → „Zlecenie”); czysta funkcja danych. Pola przejścia (`domain/transition-input.ts`): powód 1–500 znaków (NFC, przycięty), dzień zakończenia (domyślnie dziś wg `Europe/Warsaw`, `domain/business-date.ts`). Test ścieżek (BFS po grafie z rolą Edytora, generowany z tabeli) pilnuje, że Edytor nie wychodzi z `settled` / `cancelled` i nie czyści `closedAt`.
- **Kolejność w transakcji** (`application/transition-work-order.service.ts`, komentarz na górze pliku): blokada wiersza `SELECT … FOR UPDATE` z polityką odczytu (`404`) → `If-Match` (`428` / `400`) → treść (`400`) → idempotencja (przed porównaniem wersji; zakres rekordu zawiera id zlecenia) → krawędź tabeli (`409`, a przy nieaktualnej wersji `412`) → rola (`403`) → step-up przy przywróceniu (`403 step_up_required`, `stepUpFresh` z `identity` i `CLOCK`) → wersja (`412`) → pola przejścia → warunki uczestników (`422`) → `UPDATE … version = version + 1`, skutki uczestników, zdarzenie audytu. Błąd na dowolnym kroku cofa całość.
- **Port `WorkOrderTransitionParticipant`** (`transition-participant.ts`, rejestr `WorkOrderTransitionRegistry` eksportowany z modułu): `check` (kod powodu albo `undefined`) i `apply` w transakcji komendy, stała kolejność, bez zewnętrznego I/O. Brak uczestników produkcyjnych do EVM-053 (warunki spełnione); testy mają uczestnika testowego.
- **`If-Match`** (`platform/http/if-match.ts`): silny ETag `"N"` (zdolność platformy — pierwsze użycie); nowe kody `invalid_state_transition` (409), `version_conflict` (412), `transition_condition_not_met` (422), `precondition_required` (428).
- **Powód** (`status_reason`) to pole swobodne z danymi osobowymi: zostaje w kolumnie (do wpisu dziennika, EVM-038), a odczyt go nie zwraca; nigdy w audycie, logu, odpowiedzi ani rekordzie idempotencji.
- **Migracja `0016_work_order_status`** (expand): kolumny `resume_status` (cztery statusy aktywne), `status_reason` (1–500), `status_changed_at`, `closed_at`, `completed_on` — wszystkie nullable, bez backfillu.
- **Dług / uwagi:** `PATCH` pola `status` (`400 read_only_field`) — test dopisze EVM-035; brak limitu mutacji na użytkownika (SR-API-02 → EVM-067); audyt odmów przywrócenia (`outcome: denied`) — przegląd modelu zagrożeń w M1.
