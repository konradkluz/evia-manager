# Niezmienniki repozytorium (`tools/repo-policy/`)

EVM-006 (AC1–AC8; ADR-0012, ADR-0015, ADR-0016). Reguły, których nie sprawdza żadne narzędzie zewnętrzne, zapisane jako testy Vitest (TypeScript) — uruchamiane w `pnpm run gate` i w CI jak każdy workspace (`test:coverage`, próg 90%). Jedyna zależność poza wspólną konfiguracją: `yaml` (ISC, bez zależności własnych) do czytania workflowów, `compose.yaml`, `lefthook.yml`, `pnpm-workspace.yaml` i plików wyjątków.

| Plik testów               | Co pilnuje                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test/structure.test.ts`  | struktura monorepo i workspace'y (`private`, `@evia/*`, README), skrypty `lint` / `typecheck` / `test:coverage`, jedno źródło wykluczeń pokrycia, kolejność `pnpm run gate` (walidator dokumentacji zaraz po hookach — EVM-013), granice modułów, narzędzia bez zależności, Node 26 i pnpm wszędzie w tej samej wersji, ustawienia łańcucha dostaw pnpm, tylko dokładne wersje z rejestru, kontrakt `@evia/tokens`, testy czytające repozytorium poza swoim workspace'em bez cache Turborepo (`turbo.json` workspace'u: `cache: false` albo `inputs` z `$TURBO_ROOT$`) |
| `test/compose.test.ts`    | utwardzenia `compose.yaml` (digesty, bez portów, uprawnień, gniazda Dockera, `env_file`, interpolacji), Dockerfile `backend-tests`, montaże tylko z listy dozwolonych, `.scratch` wyłącznie jako wyjście, sieć skanerów, jedyne miejsce uruchamiania Dockera; reguły `ask` / `deny` / `allow` w `.claude/settings.json` (D4, RR-03) — z indeksu git, czyli to, co trafi do commita (lokalna, niezacommitowana zmiana nie jest sprawdzana — zob. RR-03 w `docs/security/threat-model.md`)                                                                                                   |
| `test/workflows.test.ts`  | workflowy: SHA akcji z komentarzem wersji, `permissions`, `timeout-minutes`, `persist-credentials: false`, brak niebezpiecznych wyzwalaczy i sekretów; kolejność etapów; krok walidatora dokumentacji (EVM-013, bramka 11: pierwszy krok `quality` przed `pnpm install`, stały skrypt `DOCS_CHECK_SCRIPT`, przekazany kod wyjścia, podsumowanie przebiegu, bez `if` / `continue-on-error` / `env` / `${{ }}`, `quality` bez `continue-on-error`, `defaults` i zmiennych spoza listy, pięć jobów); `ci-gate` i `main-integrity`; Renovate (token tylko w kroku Renovate, obraz po digeście); Docker w skryptach wyłącznie przez `docker compose -f compose.yaml run --rm`                |

| `test/exceptions.test.ts` | wyjątki skanerów: powód, właściciel, historyjka, termin (≤ 30 dni Critical/High, ≤ 90 dni pozostałe), brak wyjątków dla `MAL-…`, wąski `.semgrepignore`                                                                                                                                                                                                        |
| `test/agents.test.ts`     | model i effort każdego agenta (`.claude/agents/`) zgodne z tabelą w `workflow.md`; model historyjki w workflow `deliver-story` (prawdziwy skrypt z atrapami agentów); pole `model` w szablonie, DoR, `/refine` i `/deliver`; żadna historyjka nie obniża agenta na `opus` (EVM-074) |
| `test/docs.test.ts`       | „Szybki start” w README, „Stack i komendy” w `CLAUDE.md`, „Narzędzia” w `testing-strategy.md`, tryb scalania przez PR (D2)                                                                                                                                                                                                                                     |
| `test/checkers.test.ts`   | każdy checker z `src/` wykrywa naruszenia na danych syntetycznych — zielony test prawdziwego repozytorium coś znaczy                                                                                                                                                                                                                                           |

Jedynym workspace'em, który może łagodzić wspólne reguły ESLint i TypeScript, jest `tools/docs-lifecycle` (wyjątek z EVM-006 znosi EVM-073).
