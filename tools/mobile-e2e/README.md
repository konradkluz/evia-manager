# Test dymny Maestro na emulatorze (`tools/mobile-e2e/`)

EVM-009 AC4 (ADR-0015: E2E Android — Maestro na emulatorze Androida na Windows jest jedynym dowodem; w CI bez emulatora). Działa **bez instalacji zależności** (tylko `node:*`); procesy startowane z tablicą argumentów, nigdy przez powłokę (Gradle i Maestro przez `java -classpath …`, bo Node nie uruchamia plików `.bat` bez powłoki).

`pnpm --filter @evia/mobile run e2e` (= `node tools/mobile-e2e/cli.mjs [--skip-build] [--port <n>]`):

1. **Preflight** (`src/preflight.mjs`): `ANDROID_HOME` (domyślnie `%LOCALAPPDATA%\Android\Sdk`), `adb`, `emulator`, `JAVA_HOME` (JDK 17), Maestro (`EVIA_MAESTRO_HOME`, domyślnie `%USERPROFILE%\.evia\tools\maestro-2.11.0`) i — na Windows — **długie ścieżki** (`LongPathsEnabled`), bez których natywny build React Native się nie powiedzie (komunikat z poleceniem naprawczym).
2. **Emulator** (`src/adb.mjs`): dokładnie jeden. Gdy żaden nie działa, startuje AVD `Medium_Phone_API_35` i czeka na `sys.boot_completed`; więcej niż jeden = odmowa (maszyna uruchamia jeden naraz).
3. **Build wariantu e2e** (`expo prebuild --clean`, `gradlew assembleRelease` tylko dla ABI `x86_64`): `EVIA_BUILD_VARIANT=e2e`, adres API `http://10.0.2.2:<port>`, `EXPO_NO_TELEMETRY=1`, `MAESTRO_CLI_NO_ANALYTICS=1`; środowisko procesów to lista dozwolona (`PATH`, `JAVA_HOME`, … — żadnych tokenów hosta). Opcjonalnie `EVIA_ANDROID_CMAKE_VERSION=3.31.6` (CMake z Ninja obsługującym długie ścieżki).
4. **Serwer scenariuszy** (`src/stub-api.mjs`) na `127.0.0.1:<port>` (nigdy 0.0.0.0): `GET /api/health` w trybach `ok` / `update` (minimum 99.0.0) / `down` (503 `problem+json`); zapisuje tylko nagłówki `X-Client-Platform` i `X-Client-Version`. Od EVM-100 także cztery operacje logowania mobilnego z kontraktu EVM-090 (`login`, `login/totp`, `token`, `logout`) dla jednego syntetycznego konta (`E2E_ACCOUNT`), w trybie logowania kroku (`auth` w `src/scenarios.mjs`: `ok`, `rate_limited` — 429 z `Retry-After: 230`, `channel_not_allowed`, `version_unsupported` — 426, `session_revoked` i `device_wipe_required` przy odświeżeniu); tokeny to stałe słowa testowe (gitleaks), treści żądań nie są zapisywane.
5. **Przepływy** (`apps/mobile/e2e/*.yaml`, kolejność i stan serwera/trybu samolotowego w `src/scenarios.mjs`): online · tryb samolotowy i powrót sieci (aplikacja w tle → sieć wraca → pierwszy plan) · aktualizacja wymagana · serwer niedostępny i ponowienie · ładowanie (serwer trzyma żądanie zdrowia — tryb `hang`, szkielet). Test `test/flows.test.mjs` pilnuje zgodności przepływów ze scenariuszami i identyfikatora aplikacji. Od EVM-100 powłoka wymaga sesji: przepływy EVM-009 logują się wspólnym podprzepływem `e2e/common/sign-in.yaml` (krok `0x-sign-in.yaml` przed startem bez sieci, z serwerem niedostępnym i z trzymanym żądaniem), a scenariusze `sign-in`, `sign-in-errors`, `sign-in-blocked`, `session-revoked`, `sign-in-offline` i `sign-out` (przepływy `20`–`26`) sprawdzają M-01, M-02 i M-09.
5a. **Magazyn lokalny (EVM-093)** — przepływy `08`–`14` działają przez ukryty panel haków wariantu e2e (`apps/mobile/src/e2e-hooks/panel.tsx`, wybierany przy budowaniu przez resolver Metro `plugins/e2e-hooks-resolver.ts`; w release jest pusty slot), a kroki urządzenia (`src/device.mjs`, pole `before`/`after` w `src/scenarios.mjs`) — przez `adb` i `run-as` (wariant e2e jest `debuggable`, obraz Google Play nie ma `adb root`): `check-encrypted` (nagłówek `files/SQLite/evia.db` ≠ `SQLite format 3`, plik ≥ 4096 B, `grep -r` znacznika po całym `/data/data/<pakiet>` i `/sdcard/Android/data/<pakiet>`, `logcat -d`), `force-stop`, `kill-9` (`run-as … kill -9 $(pidof …)`), `reboot` (czeka na `sys.boot_completed`, następny przepływ ma jedną powtórkę), `copy-db` / `corrupt-db`, `check-backup-transport` (`bmgr` przez transport lokalny z pakietem kontrolnym `com.android.providers.settings`) i `adb backup` (archiwum w `.scratch/mobile-e2e/`, usuwane zaraz po ocenie). Wyniki kroków to liczby i kody, nigdy ścieżki ani treść.
5b. **AC4 EVM-093 — `adb backup` na paczce nie-debuggable (decyzja Konrada, opcja a).** Android 12+ wykonuje `adb backup` aplikacji `debuggable` niezależnie od `allowBackup` i reguł wykluczeń, a wariant e2e musi być `debuggable` dla `run-as` (AC1, AC5, AC6) — wynik na e2e nic nie mówi o paczce release. Dlatego build robi najpierw **release** (`releaseBuildEnv`: bez `EVIA_BUILD_VARIANT`, adres `https://api.example.invalid` — paczka nie jest uruchamiana), kopiuje `app-release-unsigned.apk` do `.scratch/mobile-e2e/evm093-release-unsigned.apk` i od razu uruchamia `tools/mobile-apk verify` (kod ≠ 0 przerywa), potem build e2e jak dotąd, a na końcu `zipalign -P 16` i `apksigner` kluczem debug szablonu (ścieżka na sztywno `android/app/debug.keystore`, wartości z `signingConfigs.debug` wygenerowanego `build.gradle`, hasła wyłącznie `--ks-pass env:` / `--key-pass env:` w środowisku samego `apksigner`) do `.scratch/mobile-e2e/evm093-release-debugkey.apk` i ponowny `verify`. To paczka testowa: nie trafia do `dist/` ani CI (narzędzie nie działa w CI), a `tools/mobile-apk sign` nadal odrzuca klucz debug. Scenariusz `local-store-backup`: `10-backup-seed` (e2e, 3 wpisy) → `check-backup-transport` (`bmgr` na e2e — Auto Backup respektuje reguły także dla `debuggable`) i `adb backup` e2e jako **kontrola pozytywna** (`adb-backup-control-check`: archiwum MUSI zawierać dane aplikacji — transport i parser działają; to nie jest dowód AC4) → `install-release-debugkey` (`install -r` na dane e2e; `dumpsys package` bez `DEBUGGABLE` i `ALLOW_BACKUP`, brak linii flag = błąd; `run-as` odmawia „not debuggable”; SHA-256 `base.apk` z `pm path` = plik lokalny) → `adb backup` release i `adb-backup-check` (archiwum czytelne, 0 wpisów `apps/<pakiet>/` poza `_manifest`; w szczególe linia logcat o kwalifikacji pakietu do kopii) → `reinstall-e2e` (`install -r` e2e, znów `DEBUGGABLE`) → `10-backup-after` (`queue=3`: dane były w telefonie przez cały czas). Gdy cokolwiek po `install-release-debugkey` padnie, runner na końcu scenariusza i w `finally` instaluje e2e z powrotem; nieudany powrót = pozostałe scenariusze `skipped`, kod 1. Raport podaje commit buildu, liczbę lokalnych zmian w drzewie i SHA-256 instalowanej paczki release. `--skip-build` wymaga obu APK z wcześniejszego buildu.
6. **Raport** `.scratch/mobile-e2e/report.md` (poza gitem): model i **poziom API emulatora**, wersja Maestro, wynik każdego przepływu, nagłówki zgodności na każdym żądaniu, przegląd logcat procesu aplikacji (liczby linii z adresem / słowem „token”, bez treści). Wynik zielony = wszystkie przepływy + nagłówki + czysty log.
7. **Zrzuty do przeglądu UX** (`takeScreenshot` w przepływach: S-01 online/offline/serwer niedostępny/ładowanie/po powrocie sieci, „Kolejka”, S-02): Maestro zapisuje artefakty w `.scratch/mobile-e2e/maestro-output/` (czyszczone przy każdym uruchomieniu; `--test-output-dir`), runner zbiera pliki PNG płasko do `.scratch/mobile-e2e/screenshots/` i kopiuje do `docs/ux/reviews/EVM-009/` (PNG tam są ignorowane przez git — `docs/ux/reviews/**/*.png`); nazwy z przepływów (`s01-online.png`, `kolejka-empty.png`, …) są stabilne, a raport je wymienia. Zrzuty zebrane są także po nieudanym uruchomieniu (pokazują, gdzie przepływ stanął).

**Build z krótkiego klonu (bez administratora):** `EVIA_E2E_SHORT_PATHS=1` pomija kontrolę rejestru i dopisuje do Gradle skrypt inicjujący z `-DCMAKE_OBJECT_PATH_MAX=250` (opis i kroki: `docs/ops/dystrybucja-apk-android.md`, „Droga A”). Serwer scenariuszy działa w wątku roboczym (`src/stub-worker.mjs`), bo runner blokuje swój wątek w synchronicznym procesie Maestro; emulator jest uznany za gotowy dopiero, gdy odpowiada usługa pakietów; pierwszy przepływ po świeżym starcie ma jedną powtórkę (instalacja sterownika Maestro), jawną w raporcie (`passed (retried)`, linia `Retried flows`).

Testy: `pnpm --filter @evia/mobile-e2e run test:coverage` (`node:test`, próg 90%; fałszywy host odtwarza całą sekwencję, w tym awarie na każdym kroku).
